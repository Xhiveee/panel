# AGENTS.md — Minecraft Panel

## Суть

Веб-панель для управления Minecraft-серверами (systemd + Docker) с поддержкой нескольких серверов через агентов. Простая установка, современный минималистичный дизайн, быстрая консоль и файловый менеджер (без лагов, в отличие от MCSManager).

Архитектура: **master** (веб-UI + API, одна машина) + **agent** (тонкий клиент на каждой ноде, управляет локальными systemd/docker).

Агент независим от мастера — MC-сервера не должны зависеть от доступности панели и не должны падать при отключении master.

---

## Стек

### Backend — Go

- chi — HTTP-роутер
- nhooyr.io/websocket — WebSocket
- coreos/go-systemd/dbus — управление systemd
- docker/docker/client — управление Docker
- creack/pty — консоль
- modernc.org/sqlite — БД
- golang-jwt + bcrypt — авторизация
- embed — вшивание фронта в бинарник

### Frontend — Vanilla JS (без сборщика)

- HTML генерируется на Go (html/template или .html-файлы через embed)
- CSS — прямо внутри `<style>` в HTML-шаблонах, без отдельных файлов
- Alpine.js — реактивность и биндинги без сборки
- нативный `fetch` — HTTP-запросы
- нативный `WebSocket`
- нативный History API + свой мини-роутер (или chi-роуты на страницы)
- xterm.js — консоль
- uPlot — графики
- свой минимальный стор (pub/sub) — расшаренное состояние
- ручная виртуализация списков — для больших списков (логи, файлы)

### Сборка

Один бинарник. Нет npm/Vite/бандлера — фронтенд состоит из HTML-шаблонов и нескольких статичных `.js`-файлов (Alpine, xterm.js, uPlot, собственный код), которые вшиваются в бинарник через `embed`.

## Архитектура

### Master

Master отвечает за:

- веб-интерфейс;
- HTTP API;
- пользователей и авторизацию;
- RBAC и permissions;
- управление нодами;
- связь с агентами;
- хранение состояния и конфигурации;
- метрики, если они агрегируются на уровне панели.

Master **не должен напрямую управлять systemd или Docker на удалённых нодах**.

Все локальные операции на ноде выполняет Agent.

### Agent

Agent отвечает за:

- локальные systemd-сервисы;
- локальные Docker-контейнеры;
- PTY и консоль Minecraft;
- файловую систему;
- локальные операции с инстансами;
- локальные метрики;
- выполнение разрешённых команд от Master.

Agent должен оставаться работоспособным при недоступности Master.

Не допускается архитектура, при которой отключение Master автоматически останавливает Minecraft-серверы.

## Основные правила разработки

1. Сначала изучай существующий код и архитектуру, затем вноси изменения.
2. Не переписывай рабочую архитектуру без необходимости.
3. Не добавляй зависимости, если задача нормально решается существующим стеком.
4. Не создавай абстракции заранее — абстракция должна решать реальную проблему.
5. Не дублируй бизнес-логику.
6. Backend является источником истины для состояния системы и permissions.
7. Frontend не должен самостоятельно реализовывать серверную бизнес-логику.
8. Все важные проверки безопасности должны выполняться на backend.
9. Изменение архитектуры допустимо, если текущая архитектура объективно мешает реализации или безопасности.
10. При архитектурном изменении учитывай совместимость существующих компонентов.
11. Не оставляй временные решения, mock-логику или TODO вместо основной функциональности.
12. После изменения проверяй все связанные компоненты, а не только изменённый файл.

## Master ↔ Agent

Master и Agent должны иметь чёткое разделение ответственности.

- Браузер общается с Master.
- Master общается с Agent.
- Браузер не должен напрямую управлять Docker/systemd на ноде.
- Agent не должен зависеть от браузера.
- Agent не должен содержать пользовательскую бизнес-логику Master.
- Команды между Master и Agent должны быть явно определены и валидироваться.
- Потеря соединения Master ↔ Agent не должна останавливать уже работающие серверы.
- После восстановления соединения состояние должно синхронизироваться.
- Ошибки Agent не должны приводить к падению Master.
- Недоступность отдельного Agent не должна ломать остальные ноды.

## API

API должен быть разделён по ответственности.

Примерные области:

- `/api/auth/*`
- `/api/users/*`
- `/api/nodes/*`
- `/api/instances/*`
- `/api/files/*`
- `/api/backups/*`
- `/api/metrics/*`

Не смешивать API Master с внутренним протоколом Master ↔ Agent.

Все входные данные API должны валидироваться.

Ошибки API должны возвращаться в предсказуемом формате.

Backend должен проверять:

- аутентификацию;
- permissions;
- существование ресурса;
- корректность параметров;
- допустимость операции;
- принадлежность ресурса пользователю/роли.

---

## WebSocket

WebSocket используется для:

- консоли;
- потоковых событий;
- real-time состояния;
- других операций, где обычного HTTP недостаточно.

WebSocket не должен обходить обычную систему авторизации и permissions.

Каждое WebSocket-соединение должно проверять:

- пользователя;
- authentication;
- доступ к ресурсу;
- тип разрешённой операции.

Потеря WebSocket-соединения не должна приводить к повреждению состояния сервера.

## Безопасность

Панель имеет доступ к Docker, systemd, PTY и файловой системе, поэтому безопасность является обязательной частью архитектуры.

### Авторизация

- Использовать безопасное хранение credentials.
- Пароли хранить только в виде безопасного хеша.
- JWT должен иметь ограниченный срок действия.
- Проверять срок действия и claims JWT.
- Не доверять данным, пришедшим только от frontend.
- Все privileged-операции должны дополнительно проверять permissions.

### RBAC

Permissions проверяются на backend.

Frontend может скрывать недоступные действия для удобства пользователя, но это не является механизмом безопасности.

Каждая административная операция должна проходить server-side authorization.

### Master ↔ Agent

- Agent должен аутентифицировать Master.
- Master должен идентифицировать Agent.
- Использовать уникальные credentials для каждой ноды.
- Не использовать один общий секрет для всех Agent.
- Credentials не должны попадать в frontend.
- Секреты не должны храниться в исходном коде.
- Соединение должно использовать защищённый транспорт.
- При компрометации одного Agent остальные ноды не должны автоматически считаться доверенными.

### Команды

Нельзя без необходимости передавать произвольные shell-команды.

Использовать типизированные операции там, где это возможно:

- start;
- stop;
- restart;
- status;
- logs;
- files;
- metrics;
- backup;
- restore;
- другие явно разрешённые операции.

Если выполнение произвольной команды действительно требуется, оно должно проходить отдельную проверку permissions и безопасное управление процессом.

Никогда не вставлять непроверенные пользовательские значения непосредственно в shell-команды.

### Файлы

Файловый API должен защищаться от:

- path traversal;
- выхода за разрешённую директорию;
- подмены путей;
- несанкционированного чтения;
- несанкционированной записи;
- опасных операций удаления.

Пути должны нормализоваться и проверяться до выполнения операции.

### Docker

Не предоставлять пользователю неконтролируемый доступ к Docker socket/API.

Любые операции Docker должны проходить через разрешённый backend/agent API.

Не передавать непроверенные пользовательские параметры напрямую в Docker API.

### systemd

Не разрешать произвольное управление любыми системными сервисами.

Agent должен работать только с разрешёнными Minecraft/systemd units и операциями.

### PTY / Console

Консоль должна:

- проверять permissions;
- быть привязана к конкретному instance;
- корректно закрывать PTY;
- не оставлять зависшие процессы;
- не позволять пользователю получить доступ к чужому instance.

## Данные и состояние

- SQLite используется как локальная БД панели.
- Не хранить секреты в SQLite в открытом виде без необходимости.
- Все изменения критического состояния должны быть атомарными настолько, насколько это возможно.
- Ошибка записи БД не должна приводить к неконсистентному состоянию приложения.
- Не считать frontend state источником истины.
- При восстановлении соединения состояние Agent должно синхронизироваться с Master.

## Frontend

### Рендеринг

- HTML генерируется на backend (Go `html/template` или embed-файлы .html).
- CSS пишется прямо внутри `<style>` в шаблонах, без отдельных .css-файлов.
- Не переносить бизнес-логику на клиент — frontend только отображает данные и вызывает API.

### Состояние

- Server state (данные с API: ноды, инстансы, файлы, метрики) — получать через `fetch`, хранить в простом кэше (Map/объект) с ручной инвалидацией/refetch по необходимости.
- Client-only state (UI-состояние: открытые модалки, выбранная вкладка, локальные настройки интерфейса) — хранить в Alpine.js `x-data` или в собственном минимальном pub/sub-сторе, если состояние расшарено между несколькими компонентами/страницами.
- Не смешивать server state и UI state в одном месте без необходимости — кэш API-данных и UI-флаги логически разделять, даже если оба лежат в простых JS-объектах.

### UI

- Colors: основной чёрный, акцент белый, прочие Error/Warn/Success (тёмный текст на светлом фоне, светлый текст на тёмном фоне).
- monochrome UI.
- Компоненты (модалки, dropdown, табы) писать как небольшой набор переиспользуемых HTML-шаблонов + Alpine-биндингов; не изобретать отдельный компонент под каждую страницу заново.
- Не дублировать существующие UI-компоненты без необходимости.
- Сохранять единый визуальный стиль.
- Интерфейс должен оставаться минималистичным и быстрым.
- Не перегружать страницы декоративными элементами.
- Состояния loading/error/empty должны быть предусмотрены.
- Длинные списки и файловые деревья должны использовать виртуализацию там, где это необходимо.

### Консоль

xterm.js используется для отображения терминала.

Консоль должна поддерживать потоковый вывод без постоянного полного перерендера содержимого.

Не хранить неограниченный объём вывода в памяти — ограничивать буфер (scrollback) xterm.js разумным размером.

## Производительность

Панель должна быть рассчитана на управление большим количеством:

- нод;
- Minecraft-инстансов;
- файлов;
- строк консоли;
- метрик.

Использовать виртуализацию для больших списков (рендерить только видимые строки по scroll-позиции).

Не выполнять тяжёлые операции в основном UI-потоке.

Не делать полный reload данных при каждом небольшом изменении.

WebSocket использовать для real-time данных, где это действительно необходимо.

Agent не должен блокировать обработку других операций из-за одного Minecraft-инстанса.

---

## Обработка ошибок

- Ошибки не должны игнорироваться.
- Не использовать `panic` для ожидаемых runtime-ошибок.
- Backend должен возвращать понятные ошибки.
- Frontend должен корректно отображать ошибки пользователю.
- Логи не должны содержать пароли, JWT, API keys и другие секреты.
- Ошибка одного сервера/Agent не должна приводить к падению всей панели.

---

## Логи и аудит

Логировать важные системные события:

- авторизация;
- создание/удаление пользователей;
- добавление/удаление Agent;
- запуск/остановка серверов;
- изменение конфигурации;
- файловые операции с высоким уровнем риска;
- backup/restore;
- другие privileged-операции.

Не логировать секреты и credentials.

Для критических административных операций желательно сохранять audit trail.

## Установка

Install-скрипт → бинарник + systemd unit → `systemctl start panel-master` / `panel-agent`.

Установка должна быть максимально простой и воспроизводимой.

Не требовать ручного редактирования исходного кода для базовой настройки.

Конфигурация, секреты и runtime-данные должны храниться отдельно от бинарника.

Обновление панели не должно удалять пользовательские данные и конфигурацию.

## Проверка перед завершением задачи

Перед завершением реализации:

1. Проверить сборку backend.
2. Проверить, что фронтенд-шаблоны и статичные JS-файлы корректно вшиваются через embed.
3. Проверить работу ключевых страниц в браузере вручную.
4. Запустить formatter/linter, если они настроены (gofmt/golangci-lint для backend).
5. Запустить доступные тесты.
6. Проверить связанные API.
7. Проверить permissions для изменённых privileged-операций.
8. Проверить обработку ошибок.
9. Проверить, что секреты не попали в код, логи или frontend.
10. Не оставлять сломанные временные решения.

Если полноценный тест невозможен, явно указать причину.
